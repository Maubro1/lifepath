# Tracking Under Pressure (v0.3.1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Keep train and other low-accuracy fixes, tell pottering from leaving with the step counter, save GPS effort when it only yields rough fixes, draw better walking and vehicle lines, and make the map live and steady.

**Architecture:** A new point kind `rough` carries fixes above the accuracy ceiling past the live filter into the diary; the offline smoother and the map judge them. The motion engine gains walked-distance and drift evidence for wake decisions and a struggle state for vehicles. The map diffs overlays by key and reloads live while visible.

**Tech Stack:** Swift 6, Core (Foundation only, tested locally and on CI), Diary (GRDB, CI only), app (SwiftUI/MapKit/CoreLocation/CoreMotion, CI build only).

**Spec:** `docs/superpowers/specs/2026-11-16-tracking-under-pressure-design.md` (read it first; this plan argues from it).

## Global Constraints

- Top priority: accuracy, battery efficiency and a cool phone, together; prefer sensors already running over switching GPS on.
- Stored points are never modified; migrations are additive; unknown point kinds read as `.moving` (Diary.swift:326) and must stay so.
- Every shortcut gets `// shortcut: <limit>, <when to upgrade>`.
- Test fixtures are synthetic (public repo).
- Commit trailer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Local tests: `pwsh -NoProfile -File scripts/test-core.ps1 [--filter X]`; CI: push, then `bash scripts/ci-wait.sh <sha>`.

## Review Focus

- A long train ride (60 min of rough fixes, no steps): one trip, no gaps, GPS in hundred-metre mode for all but the probes.
- Rough fixes interleaved with good ones in a city (hAcc swinging 40↔90 m): the precise line must not be pulled by rough fixes; trips must not split.
- A phone left on a table at home with occasional pocket steps: never wakes GPS for more than 2 min per hour.
- Downgrade to v0.3.0 after recording rough points: they read as `.moving` and appear in lines (accepted; note in decisions).
- Leaving home on a bike with the phone in a bag (no steps): the geofence/keep-alive still starts GPS.

### Task 2: Smoother judges rough stretches, removes spikes, uses walking pace

**Files:** Modify `Core/Sources/Core/TripSmoother.swift`, `LifePath/Map/SmoothingService.swift`, `LifePath/Recorder/MotionService.swift`; Test `TripSmootherTests.swift`.

**Interfaces:**
- Produces: `TripSmoother.smooth(_ fixes: [Sample], rough: Set<Int> = [], pace: [(t: Date, speed: Double)] = []) -> [(t: Date, lat: Double, lon: Double)]` (indices of rough fixes; pace = pedometer speed per 30 s bucket start). `TripSmoother.version = 2`. `MotionService.pace(from:to:) async -> [(t: Date, speed: Double)]` (30 s buckets of `CMPedometerData.distance`).
- Consumes: Task 1's `.rough` kind (SmoothingService builds `rough` from it).

- [ ] Failing tests: `testRoughStretchWeightedByConsistency` (spec's train fixture: smoothed within 60 m of truth), `testSpikeRemoved` (10 m/s route, 3-fix 150 m excursion → deviation ≤ 20 m), `testWalkingPaceStraightensZigzag` (spec's canyon fixture: path length within 15% of pedometer distance and mean error below `smooth` without pace), existing tests unchanged.
- [ ] Implement: rough effective σ = clamp(robust spread of second differences / √6, 20, hAcc); spike = run ≤ 3 fixes within 30 s implying speed above 4 m/s (walk median < 2.5), 15 m/s (< 7) or 3 × median, with neighbours aligned within their accuracy → r = 1e4; pace used as speed along own heading (σ 0.3 m/s) where the fix lacks valid Doppler, walking trips only, pace only within 7 days.
- [ ] SmoothingService: store the smoothing version in `meta` and re-smooth all trips once when it changes (keep the existing cursor logic; reset cursor to start).
